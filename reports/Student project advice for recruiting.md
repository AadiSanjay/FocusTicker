# Ship small, explain everything, skip Kubernetes

FocusTicker is already the scarce thing in student recruiting, but only for one reason: real people use it. In 2024–2026 the advice from hiring managers, career guides and respected engineers points the same way. A shipped project with real users, which you can defend line by line, beats a technically ambitious one that is unfinished or AI-scaffolded. With AI-tailored resumes flooding every pipeline, verifiable signals (a public install count, months of commits, real bug reports) are worth more than they were five years ago. Notes from Dan McKinley, DHH, Martin Fowler and Dan Luu agree on the right engineering level for a solo project: one TypeScript service, one Postgres database, managed hosting, a few integration tests on the risky logic, and a 20-line CI file. Microservices, Redis, Kubernetes and multi-environment pipelines are the textbook over-engineering. AI tools change the advice mostly by raising the bar for understanding. Randomized studies show unguarded AI use cuts later comprehension, and interviewers now probe with "why" follow-ups built to expose code the candidate didn't write. On scoping, the plan has about 190 hours, so fix the time and vary the scope. Ship the user-requested features first. Then build a thin end-to-end sync slice before Google sign-in. Have a pre-agreed cut list ready for when the semester bites. One timing correction: most Summer 2027 Big Tech windows closed in August–September 2026, so the realistic target for this project is the Summer 2028 cycle. That cycle opens around July–September 2027, which makes a polished, metric-backed project by June 2027 the goal that matters.

## Real users beat complexity, and 79 users is a real signal

Almost every source puts "shipped and used" above "complex." Wellfound CEO Amit Matani, quoted by Gergely Orosz in November 2025, says the junior profiles that get recruiter outreach show **"projects which clearly demonstrate they can build production-ready software"** ([Pragmatic Engineer](https://newsletter.pragmaticengineer.com/i/178001705/junior-engineer-hiring-to-rebound)). A Big Tech interviewer on Taro makes the same point from the other side. Big Tech uses "pretty much every conceivable tech stack," so it hires on fundamentals, and the best way to impress is to build projects that actually have users ([Taro](https://www.jointaro.com/question/c0DiG5ureLbkZ1mKD9Rf)). Practitioner forums give the mechanism: real users surface edge cases, slow screens and confusing flows that a tutorial clone never meets, and that produces the bugs and tradeoffs interviewers want to hear about ([Hashnode](https://hashnode.com/forums/thread/your-portfolio-projects-need-real-users-not-just-code)). An F-1 career guide puts it bluntly: five strangers using your tool weekly beat a thousand stargazers ([f1jobs.io](https://www.f1jobs.io/resources/blog/side-projects-that-get-f1-hired)).

No source names a user-count threshold, and none discusses Chrome extensions specifically. The fair reading is that 79 real users with an all-5-star rating puts FocusTicker above the median student project, which has zero users. It still won't carry a resume alone. A Blind new-grad thread notes that side projects rarely change interview outcomes unless they are "genuinely impressive" ([Blind](https://www.teamblind.com/post/when-it-comes-to-side-projects-what-matters-more-quality-or-quantity-5tetlqsa)). At Google and Meta the intern bar is still set mostly by algorithmic coding rounds. A September 2025 interviewing.io survey found **none of 53 Big Tech interviewers said their company had dropped algorithmic questions** ([Pragmatic Engineer Pulse #146](https://newsletter.pragmaticengineer.com/p/the-pulse-146)). The project gets you noticed and gives you something to talk about. LeetCode-style practice still has to run alongside it.

The market makes the users more valuable, not less. Orosz reports that **1,000+ applicants for a single role is not uncommon**, that one startup received 23,000 applications in 30 days for eight roles, and that hiring managers see resumes "clearly tailored by AI" from people who lack the claimed qualifications ([Pragmatic Engineer, 2025](https://newsletter.pragmaticengineer.com/p/state-of-the-tech-market-in-2025-hiring-managers)). Penn Career Services, writing in August 2026, frames the new trap as "You are real and you look manufactured." Its fix is longevity: **"A profile with two years of small activity beats a perfect one built last month"** ([Penn Career Services](https://careerservices.upenn.edu/blog/2026/08/13/you-are-real-now-prove-it/)). A public Chrome Web Store install count, version history and dated user reviews are hard to fake. That provenance is the project's main recruiting asset, and the plan should protect it: keep ratings high, keep shipping, keep the history visible.

Depth beats breadth just as consistently. The Tech Interview Handbook recommends at least two projects and says a few strong achievements beat many average ones ([Tech Interview Handbook](https://www.techinterviewhandbook.org/resume/)). Extern's October 2026 Microsoft Explore guide says a finished project you can explain beats several unfinished ones ([Extern](https://www.extern.com/post/microsoft-explore-internship-guide)). The natural shape for a first-year student is one flagship that keeps getting better (FocusTicker), plus one smaller project that shows a different skill. Sustained iteration through a v2, a migration and a test suite is itself the depth signal.

## Presentation decides whether anyone notices

Recruiters skim resumes for keywords, so the resume bullet does most of the work. The Handbook's pattern is "[Accomplishment summary]: [Action] that resulted in [quantifiable outcome]". It also says to link every project name and to mirror the job description's language ([Tech Interview Handbook](https://www.techinterviewhandbook.org/resume/)). Exaggeration is a trap, because inflated descriptions "will come to light in the interview" ([Educative](https://www.educative.io/blog/3-quick-projects-boost-software-engineering-resume)) and Chrome Web Store counts are public. Say "79 users" (or whatever the store shows), not "hundreds."

The README, demo GIF and commit history serve the smaller group of engineers who click through. In 2025–2026 they also act as proof of authorship. One 2025 account says recruiters now ask outright, "did you scaffold this with a template?" ([dev.to](https://dev.to/dhruvjoshi9/junior-dev-resume-portfolio-in-the-age-of-ai-what-recruiters-care-about-in-2025-26c7)). The red flag recruiters describe is an AI-generated app pushed in one commit and called a portfolio ([Slategit](https://slategit.com/blog/ai-generated-github-projects-recruiters-suspicious-2026)). The fix for "uncontextualized AI output" is a README that documents decisions, tradeoffs and your own role ([The New Stack](https://thenewstack.io/how-ai-changes-developer-portfolios/); [Artech](https://www.artech.com/blogs/ai-assisted-portfolio-credibility)). A short decision log may be the cheapest way to make judgment visible. That addresses what Orosz calls the "illegible nature" of engineering talent ([Orosz](https://www.goodreads.com/author_blog_posts/26142196-the-illegible-nature-of-software-development-talent?tab=book)).

Interviews then test whether the presentation holds up. Ashby's deep-dive guide lists the focus areas as key decisions and their tradeoffs, the surrounding context, and challenges or lessons "after release" ([Ashby](https://www.ashbyhq.com/resources/engineer-past-projects-deep-dive)). Candidate reports collected by Exponent and Prachub describe interviewers going deep: "which decision would you reverse today, and what would changing it cost now?" ([Exponent](https://www.tryexponent.com/questions/1183/project-trade-off-experience); [Prachub](https://prachub.com/interview-questions/defend-the-trade-offs-in-one-project)). Microsoft Explore adds a product question about improving an app you use ([Extern](https://www.extern.com/post/microsoft-explore-internship-guide)). A student with 79 real users can answer every one of those from experience. A student with a tutorial clone can't. Most deep-dive guides target experienced hires, so at the intern level expect project talk in behavioral and "tell me about yourself" segments. Prepare a two-minute version and a ten-minute version.

## Right-sized engineering means one service, one database and tests on risky code

The classic essays still frame this question and point the same way. McKinley's "Choose Boring Technology" gives a team about three "innovation tokens." It warns that **"Adding the technology is easy, living with it is hard"** and advises picking "the smallest set of tech that covers our problem domain" ([boringtechnology.club](https://boringtechnology.club/)). DHH's "Majestic Monolith" calls microservices a way to parallelize thousands of developers. For small teams, copying them is cargo culting: Basecamp ran six platforms from one monolith with about 12 programmers ([Signal v. Noise](https://signalvnoise.com/svn3/the-majestic-monolith/)). Dan Luu points to Wave, a $1.7B fintech with about 70 engineers running a Python monolith on Postgres, which spent its complexity budget only where it was forced to ([danluu.com](https://danluu.com/simple-architectures/)). The 2024–2026 "just use Postgres" discussion says the same for a student stack. Postgres covers queues (`SKIP LOCKED`), caching and JSON, so add Redis only after measuring a bottleneck ([AmazingCTO](https://www.amazingcto.com/postgres-for-everything/); [Xata](https://xata.io/blog/is-postgres-really-enough-in-2026)). Solo-developer posts describe weeks lost to Kubernetes on projects with no users as "procrastination that feels like progress" ([DEV](https://dev.to/ntty/stop-over-engineering-your-indie-project-3j0h)).

For a 79-user extension, over-engineering looks like this: microservices, Kubernetes or Helm, Kafka or RabbitMQ, Redis caching, GraphQL with a single first-party client, staging plus QA plus prod, Terraform, and Nx or Turborepo for two packages. The honest exception is a project whose stated goal is to learn one of these tools, which commenters accept ([Hashnode](https://hashnode.com/forums/thread/your-hobby-project-does-not-need-to-scale-to-millions-of-users-yet)). FocusTicker's goal is a product with users, so that exception doesn't apply. A written note in the repo such as "considered Redis; Postgres handles our load" probably impresses an interviewer more than Redis itself would. That is an inference, though it fits how these engineers judge good work.

Fowler's YAGNI essay carries the caveat people forget. Deferring speculative features does **not** excuse skipping refactoring, self-testing code or continuous delivery, because those practices are what make deferral safe ([martinfowler.com](https://martinfowler.com/bliki/Yagni.html)). For how much to test, Kent C. Dodds's trophy model sums it up as **"Write tests. Not too many. Mostly integration,"** with static types and linting as the base layer ([kentcdodds.com](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications)). Fowler adds that arguing about test percentages is "a distraction" and that the real goal is fast, reliable tests that fail only for useful reasons ([martinfowler.com](https://martinfowler.com/articles/2021-test-shapes.html)). Indie developers disagree about testing MVPs at all ([Indie Hackers](https://www.indiehackers.com/post/dont-write-tests-for-your-mvp-7d9da5ee98)). That argument is about unvalidated products, though, and FocusTicker is validated and about to hold users' data on a server. The sensible middle is roughly a dozen tests on the risky logic and CI that runs typecheck, lint and tests on push from the day the server boots ([DEV](https://dev.to/oranguengineer/add-ci-when-the-project-can-boot-not-when-it-feels-finished-20m9)). The risky logic is auth required on every route, user A unable to read user B's data, idempotent sync upserts, extension storage migrations, and migrations applying cleanly. Coverage targets at this scale are theater. Broad Playwright end-to-end suites can wait, apart from perhaps one happy path later.

Some production practices aren't optional once user data reaches a server. Google's documentation says to verify ID tokens server-side with an official library: check `aud`, `iss` and `exp`, never trust a client-supplied ID, and key users on `sub` rather than email, because email "can be changed by the user" ([Google Identity](https://developers.google.com/identity/sign-in/web/backend-auth)). Beyond that, the minimum is secrets in environment variables, versioned migrations, backups you have actually test-restored, a free-tier error tracker, and rate limiting on auth and write endpoints. Solo-production checklists warn that "monitoring untested backups is just theater" ([DEV](https://dev.to/whoffagents/solo-developer-production-setup-vercel-neon-sentry-and-zero-devops-gjb)). The lightweight process to keep is issues used as a working notebook, Simon Willison style ([simonwillison.net](https://simonwillison.net/2022/Oct/29/the-perfect-commit/)), a curated decision log, and a changelog tied to store releases. Skip self-approval ceremonies, sprint boards and an ADR for every choice, which one solo developer found turned documenting into a substitute for shipping ([DEV](https://dev.to/michelfaure/what-74-adrs-in-70-days-actually-buy-a-solo-dev-no-hire-no-clients-just-the-file-13nn)).

Hosting has free-tier traps that matter for an extension making background sync calls. Render's free web services sleep after 15 minutes and take up to about 30 seconds to wake ([Render community](https://community.render.com/t/do-web-services-on-a-free-tier-go-to-sleep-after-some-time-inactive/3303)). Supabase pauses free projects that go inactive ([Supabase](https://supabase.com/docs/guides/platform/free-project-pausing)). Neon's free compute scales to zero but wakes in a few hundred milliseconds ([Neon](https://neon.tech/docs/introduction/scale-to-zero)). Neon Postgres plus a cheap always-on API instance is the boring, low-ops choice. Auth sits between learning and shipping. Lucia deprecated its library in March 2025 and turned it into a guide to writing sessions yourself ([lucia-auth.com](https://lucia-auth.com)). That supports a middle path: library-verified Google tokens plus your own small sessions table. It teaches the flow interviewers ask about without hand-rolling crypto, which Clerk or Supabase Auth would hide from you.

## AI tools raise the bar for understanding

Respected practitioners draw the same line. Karpathy coined "vibe coding" in February 2025, meaning you "forget that the code even exists." He called it fine for "throwaway weekend projects" ([Simon Willison](https://simonwillison.net/tags/andrejkarpathy)). He then wrote his own serious 2025 project, nanochat, almost entirely by hand because agents were "net unhelpful" on novel code ([Analytics India Mag](https://analyticsindiamag.com/ai-news-updates/andrej-karpathy-says-nanochat-is-entirely-hand-written-not-vibe-coded/)). Willison's rule is the clearest portfolio standard: **he won't commit code he couldn't explain to someone else** ([simonwillison.net](https://simonwillison.net/2025/Mar/19/vibe-coding/)). His "vibe engineering" essay lists what makes agents work: tests (test-first is "particularly effective with agents"), plans, CI, git discipline and review. His summary is that AI "amplifies existing expertise" ([simonwillison.net](https://simonwillison.net/2025/Oct/7/vibe-engineering/)). Addy Osmani's "70% problem" names the junior trap. Seniors use AI to speed up work they already understand. Juniors use it to find out what to do, and they accept wrong answers, miss security problems and can't debug the result ([Osmani](https://addyo.substack.com/p/the-70-problem-hard-truths-about)). Kent Beck's "augmented coding" keeps the hand-coding values, "tidy code that works," and enforces TDD. He caught the AI trying to disable tests ([Kent Beck](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes)).

The learning research is consistent, though the samples are small. In Anthropic's January 2026 randomized trial, 52 mostly junior engineers learned an unfamiliar async library. **The AI group scored 50% on a follow-up quiz versus 67% for hand-coders, with the biggest gap on debugging,** and gained only an insignificant two minutes ([Anthropic](https://www.anthropic.com/research/AI-assistance-coding-skills)). How people used AI mattered more than whether they used it. Delegation and "iterative AI debugging" (pasting errors until they go away) scored below 40%. Generating code and then interrogating it, or asking only conceptual questions, scored 65–86%. A PNAS study of about 1,000 students found **unrestricted GPT-4 raised practice scores 48% but cut later unaided exam scores 17%**, while a hints-only tutor caused no harm, though it brought no gain either ([Wharton Knowledge](https://knowledge.wharton.upenn.edu/article/without-guardrails-generative-ai-can-harm-education/)). METR found experienced developers 19% slower with AI while believing they were 20% faster ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). So a student's own sense of speed or learning isn't reliable evidence.

Hiring has split in two. Canva expects candidates to use Copilot, Cursor or Claude in interviews. It grades whether you can "read, understand, and improve" AI code, and it finds candidates with little AI experience do worse ([Canva](https://canva.dev/blog/engineering/yes-you-can-use-ai-in-our-interviews)). Shopify calls reflexive AI use a baseline expectation ([Shopify](https://www.shopify.com/careers/candidate-guide/ai-usage)). Anthropic's own live interviews and take-homes, by contrast, are "all you" unless stated otherwise ([Anthropic](https://www.anthropic.com/candidate-ai-guidance)). Interviewers have adapted to catch borrowed understanding: 81% of Big Tech interviewers in the 2025 survey suspected AI cheating, and their counters are "why" questions, granular follow-ups, re-asking later, and rapid-fire questions ([Pragmatic Engineer Pulse #146](https://newsletter.pragmaticengineer.com/p/the-pulse-146)). A student needs both skills: coding unaided, and driving an agent under discipline. For FocusTicker that means hand-writing the core the interviewer will ask about (the sync model, token verification, tracking accuracy). Agents can handle boilerplate, config, dashboard UI and test scaffolding, behind tests and small commits. A short "how I used AI" section in the README, naming what the agent got wrong, shows exactly the fluency Canva grades. That last suggestion is inferred, since no employer has published portfolio guidance on it.

## Fix the time at 190 hours and let scope give

Eight hours a week from late November to mid-May is about 24 weeks, or **roughly 190 hours before exams and slippage**. That is enough for one solid backend, not for everything on a wish list. Basecamp's Shape Up gives the frame: **"Appetites start with a number and end with a design."** Time is fixed, scope varies, and "scope hammering" is the default response to slipping ([Shape Up ch. 3](https://basecamp.com/shapeup/1.2-chapter-03)). Its build advice fits this backend exactly. Get one demoable front-to-back piece working in about the first week, with temporary auth and hard-coded values allowed. "Start in the middle" with something core, small and novel, not with login ([Shape Up ch. 11](https://basecamp.com/shapeup/3.2-chapter-11)). Cockburn's walking skeleton is the same idea: a tiny end-to-end path through every architectural component ([Code Climate](https://codeclimate.com:443/blog/kickstart-your-next-project-with-a-walking-skeleton)).

On tutorials versus projects, the advice is project-first with small, bounded study up front. freeCodeCamp and daily.dev suggest about 20% docs and 80% building, learned just in time ([daily.dev](https://daily.dev/blog/how-to-escape-tutorial-hell/)). Their test for tutorial hell is whether you can explain what your tools actually do ([freeCodeCamp](https://www.freecodecamp.org/news/how-to-learn-from-coding-tutorials-and-avoid-tutorial-hell/)). SQLBolt's 18 interactive lessons are the standard fast SQL primer ([SQLBolt](https://sqlbolt.com/)). The Odin Project teaches Node, Postgres and auth by building and deploying a project, not through lectures ([The Odin Project](https://www.theodinproject.com/lessons/node-path-nodejs-members-only)). One forum reply gives the right order: get an API passing data between client and database before touching auth ([freeCodeCamp forum](https://forum.freecodecamp.org/t/what-should-a-beginner-focus-on-when-learning-backend-development/799729)). For TypeScript, the official handbook recommends incremental migration with `allowJs` and `checkJs`, renaming one file at a time ([TypeScript Handbook](https://www.typescriptlang.org/docs/handbook/migrating-from-javascript.html)). One 2026 guide argues migration often isn't worth it under about 1,000 lines ([OneUptime](https://oneuptime.com/blog/post/2026-01-24-migrate-javascript-to-typescript/view)). FocusTicker's extension is about **1,300 lines across `background.js` (334) and `content.js` (927)**, so it sits right at that line.

The hardest part may not be what it looks like. General sync is hard; Ink & Switch say ad-hoc merge code tends to be "unreliable and brittle" ([Ink & Switch](https://www.inkandswitch.com/essay/local-first/)). But conflicts only arise when users "concurrently modify the same property of the same object" (same source), and FocusTicker's usage data doesn't do that. Each device writes its own per-day, per-site counters. Rows keyed on (user, device, date, site) with idempotent upserts can't conflict, and the dashboard just sums across devices. Server-authoritative designs like this are the mainstream alternative to CRDTs ([Jamsocket](https://jamsocket.xyz/blog/you-might-not-need-a-crdt); [PowerSync](https://powersync.com/blog/why-cinapse-moved-away-from-crdts-for-sync)). Only settings and custom-site lists need per-field last-write-wins. "Why I didn't need a CRDT" is a better interview story than a CRDT library would be. Google sign-in, meanwhile, is mostly plumbing. The traps are extension-ID and client-ID mismatches in `chrome.identity`, redirect URIs, and consent screens ([Chrome docs](https://developer.chrome.com/docs/apps/app_identity)).

The Chrome Web Store adds two external risks the schedule has to absorb. Reviews usually finish "within a few days, but it can take up to a few weeks." Broad host permissions and significant code changes draw closer scrutiny ([Chrome review process](https://developer.chrome.com/docs/webstore/review-process)), and developers reported updates stuck for 11+ days in 2025–2026 ([chromium-extensions](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/tJfyKrk2rdg)). More dangerous for a 79-user base: **if an update adds a permission that triggers a new warning, "the extension will be disabled until the user accepts the new permission"** ([Chrome permission warnings](https://developer.chrome.com/docs/extensions/develop/concepts/permission-warnings)). This matters before the backend does. The current manifest hard-codes content scripts for ten sites, so the user-requested "custom sites" feature needs host access to arbitrary domains. Requested at install time, that is exactly the broad permission that both disables existing installs and triggers extra review. The store's August 2026 update also weights recent reviews more heavily ([Chrome blog](https://developer.chrome.com/blog/cws-review-updates-2026)). Steady small releases that answer user requests therefore keep the rating fresh, and a botched permission update could put recent 1-star reviews right where they count most.

## Concrete recommendations for FocusTicker

**Reset the recruiting target.** It is November 22, 2026. Google's Summer 2027 BS intern window ran until about September 25, 2026 ([Google Careers](https://google.com/about/careers/applications/jobs/results/100648618540573382-software-engineering-intern-bs-summer-2027)), and Simplify's tracker shows most deadlines clustered in late August ([SimplifyJobs](https://raw.githubusercontent.com/SimplifyJobs/Summer2027-Internships/dev/README.md)). Microsoft Explore's monthly windows (likely December 1–7) are posted for **second-year** students, and no first-year track had appeared as of October 2026 ([Extern](https://www.extern.com/post/microsoft-explore-internship-guide)). Google STEP has no Summer 2027 posting ([Extern](https://www.extern.com/post/google-step-program-guide)). Ford Ignite takes first- and second-years until January 1, 2027 ([CMU list](https://www.cmu.edu/career/students-and-alumni/early-engagement/freshman-sophomore-summer-opportunities-2027.pdf)). This week, put FocusTicker on the resume as it stands ("Chrome extension, 79 users, 5.0 rating," linked to the store) and apply to whatever is still open, including mid-size companies and startups. Treat Summer 2028 as the real target. Its windows should open around July–September 2027, with freshman and sophomore programs around October 2027. So the true deadline for a recruiting-ready project is **end of June 2027**, and mid-May is the build deadline with a month of polish after it.

**Run the semester as five fixed-appetite cycles with a pre-agreed cut list.** The dates below assume about 8 hours a week and leave room for finals, winter break and store-review delays.

| Cycle | Dates (approx.) | Appetite | Ships | Done means |
|---|---|---|---|---|
| A: user requests | Nov 24 – Dec 19 | ~24 hrs | Timer color shift/pulse; custom sites via **optional host permissions** requested at runtime | v1.1 live in the store, requesters thanked in replies, no installs disabled |
| B: local history | Jan 12 – Feb 6 | ~24 hrs | Daily stats popup backed by per-day, per-site local records; short onboarding | v1.2 live; the local data model is the one sync will upload |
| Learning cool-down | Feb 9 – Feb 20 | ~12 hrs | SQLBolt; convert `background.js` to TypeScript with `allowJs`; set up repo CI | `tsc --noEmit`, lint and tests run on every push |
| C: walking skeleton | Feb 23 – Apr 3 | ~45 hrs | Node+TS API, Neon Postgres, deployed always-on; dev build posts day totals with a **hard-coded dev token**; one read-only dashboard page | A dev build on two Chrome profiles shows summed totals on the dashboard |
| D: real accounts | Apr 6 – May 8 | ~35 hrs | Google sign-in (`chrome.identity` + server-side `google-auth-library`), `sub`-keyed users, sessions table, opt-in sync, updated privacy policy | v2.0 submitted to the store with sync off by default and permissions optional |
| Buffer and polish | May 9 – Jun 30 | ~30 hrs | Store review, bug fixes, README, GIF, write-up | Recruiting-ready package complete |

The scope order matters more than the dates. Lead the backend with the sync slice, not Google sign-in, as Shape Up says. Develop sync against an unpacked dev build so production users never see half-built features. Batch every backend-related extension change into one store submission, so review delay and any permission prompt happen once. Decide the cuts now, in this order: (1) the rich dashboard shrinks to a single read-only page or a "synced from N devices" line in the popup; (2) two-way settings sync becomes upload-only usage sync; (3) onboarding polish goes. If Cycle C isn't working by early April, cut, don't extend. The appetites in the table are estimates; no published benchmark exists for how long beginners take to deploy Node, Postgres and auth.

**Engineer it boringly and write down why.** Use one repo with `extension/` and `backend/` folders and a small shared types file. Skip workspaces tooling unless it starts to hurt. Build one Express or Fastify service with REST/JSON and one Postgres schema managed by a migration tool checked into the repo. Use the sync design above: `UPSERT` on (user_id, device_id, date, site), storing each device's absolute daily total so retries are safe, `SUM` across devices for the dashboard, and per-field LWW only for settings. Add no Redis, queues, GraphQL, Docker-in-production, staging environment or Kubernetes. Do add Sentry's free tier, rate limiting on auth and sync routes, CORS locked to the extension origin and dashboard domain, secrets in host env vars, and one real test-restore of a backup. Write about a dozen integration tests against a real test database, aimed at auth, cross-user isolation, idempotent upserts and storage migration. Add each test alongside the code it covers, not in a testing sprint at the end. Keep `docs/DECISIONS.md` (already in the repo) to five to ten curated entries: why Postgres, why not a CRDT, why library-verified tokens plus your own sessions, why optional permissions, why this host. Those entries are your interview answers, written in advance.

**Use AI like an engineer, not a passenger.** Hand-write the first version of each new concept: the first endpoint, the schema, the upsert, token verification, and the tracking-accuracy logic in the MV3 service worker. Let an agent do the second through Nth repetitions, dashboard UI and config, behind tests. Never paste an error into a chat before forming your own hypothesis. Ask "what does this mean," not "fix this." After any generated chunk, explain it aloud without the chat open, and don't commit what you can't explain. Before interviews, re-implement the sync endpoint from scratch without AI. Add a short "How I used AI" section to the README that names one bug the agent introduced and how you caught it. Keep commits small and meaningful, because the history is now your proof of authorship.

**Package it for a 30-second skim and a 10-minute grilling.** Your resume bullet should look like "Built and shipped FocusTicker, a Chrome extension used by N users (5.0★); designed an idempotent cross-device sync backend (TypeScript, Node, Postgres, Google OAuth)…", with the name linked to the store listing. Put a 10–20 second GIF at the top of the README, then a one-line "why," a small architecture diagram, key decisions, known limitations and the AI-usage note. Write one blog-length piece on the hardest bug or the "no CRDT needed" design. Rehearse the two-minute and ten-minute walkthroughs, including "what would you reverse today." Keep up LeetCode-style practice every week alongside the build, because no amount of project polish replaces the algorithmic round at Google or Meta. Grow users opportunistically, for example by posting where productivity-minded students gather. Keep reporting the number honestly.

## Conclusion

The research changes the question. For this student, what matters is not whether the backend is impressive enough but whether the project stays real and explainable. In an AI-flooded market, what separates candidates is evidence that can't be generated: strangers using the thing, a dated history of responding to them, and an owner who can defend every tradeoff under follow-up questions. That flips some instincts. The simplest sync design is the better interview story. The permission model of a "small" custom-sites feature carries more user risk than the whole backend. Mid-May is a build deadline, not a recruiting deadline, because the cycle that matters opens in summer 2027.

The uncertainties are real and worth stating. No source measures how much users raise intern callback rates. The AI-learning studies are small and short-term. Freshman and sophomore programs (STEP, Explore's first-year track, Meta University) appeared or vanished from one cycle to the next in 2025–2026. The robust strategy holds up anyway: ship user-requested features through spring, build one honestly hard backend slice, document the reasoning, practice algorithms alongside, and apply broadly the moment postings open.
